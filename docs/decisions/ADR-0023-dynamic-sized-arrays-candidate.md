# ADR-0023: Dynamic-sized arrays — one heap tier of unknown-at-compile-time length

Date: 2026-07-18 · Status: **accepted — decided by Sapir 2026-07-18 (S14), scheduled post-M5, with Sapir's allocator amendment (see the Acceptance amendment at the end).** Q1 (surface syntax) / Q2 (growable) / Q4 (naming) remain open — the orchestrator's leans stand as proposals; Q3 is answered by the amendment. Number final: ADR-0023.

## Context (what forced the decision; spec refs)

Core arrays are exactly `[T; N]` with literal `N`: `n` is part of the type (`flow_ir::Ty::Array { elem, size: u64 }`, `crates/flow-ir/src/ty.rs:48`), storage is static (stack allocas today, `crates/backends/llvm/src/func.rs:196–215`), and every bound is a compile-time constant (`guard_index(&i64idx, size: u64)`, `func.rs:608`). ADR-0021 kept it that way deliberately: its non-goals record "dynamic array sizes (`[T]`): out, unchanged… dynamic `n` requires heap allocation and reopens [E3]… Reopening is its own ADR." This is that ADR — written as a **candidate**, because the pinned reopen trigger has been reached on paper: `flow-as-implemented.md` §5 item 3 records E3 as vacuous-by-proof with "the first heap-op ADR (dynamic arrays being the expected one)" as the trigger.

Why dynamic sizing is wanted, with repo evidence rather than appeal:

- **The user guide already teaches it and cannot run it.** §8.2's array sum is `fn sum_array(arr: [i32])` and §8.4's matmul is `fn matmul(a: [[f32]], b: [[f32]])` — both badged "Core+1 — does not compile today", rejected P0104. Real kernels do not know their extents at compile time: image dimensions arrive with the input, and the fixed-`N` workaround is exactly the unrolled-literal shape `vector_add.flow` exists to document.
- **`vector.flow`'s aspirational dialect** wants size-flexible kernels; its `[A; N]`-with-variable half is ADR-0024's tier, but the file is the standing exhibit that the current tier ladder stops too early (design note `2026-07-16-sizes-generics-execution-graphs.md` §1: the v0.2 corpus sketches *three* dynamic collections — `[T]`, `Vec<T>`, `Stream<T>` — with no unifying semantics).
- **The machinery is half-built and waiting.** The spec's `Ty` already admits unknown size (`Array { elem, size: Option<usize> }`, category-ir §3.4 — the realized IR narrowed it to `u64`); the parser already parses `[T]` and keeps `TyKind::Dynamic` for span-precise rejection (`crates/flow-syntax/src/parser.rs:674–714`); the interpreter's array value is already a runtime `Vec` (`RValue::Array(Vec<RValue>)`, `crates/flow-interp/src/value.rs:23`); and the last-use frontier (category-ir §9.4/§10) is specified machinery with zero consumers (`array-scale-plan.md` W1: heap lowering "would be that machinery's first real consumer").

This candidate follows the roadmap discussion recorded in `notes/2026-07-16-sizes-generics-execution-graphs.md` (Tier C of its four-tier ladder) and the heap-lowering option in `notes/array-scale-plan.md` (W1, option 1a). HANDOFF §4.2 lists dynamic arrays as Core+1; ADR-0021 glosses the order as "after coproducts" (HANDOFF §4.2 itself lists without ordering — see Open questions).

## Decision (imperative, if accepted)

1. **One new type former: the fixed-but-unknown-size heap array.** A dynamic array is a dependent pair `(n, data)` — `Vec T ≅ Σ_{n:ℕ} [T;n]` (design note Tier C) — with the length carried **in the value, not the type**, and **immutable after creation**. Surface spelling tentatively `[T]` (the already-parsed form; P0104 flips to acceptance; final spelling is Open question Q1). IR: one variant, `Ty::ArrayDyn { elem }` (equivalently, restore spec §3.4's `size: Option` and take `None`; one former either way — dedupe at implementation). **The named alternative is the bounded-dynamic tier `[T; ≤N]`** (design note Tier B: runtime length, static capacity, `Σ_{n≤N} [T;n]`): it keeps E3 fully intact and is total on all three backends including Verilog, but it lands in Core+1's coproduct machinery and does not serve the motivating kernels (a matmul over `[[f32; ≤4096]]` still pays capacity everywhere). Recorded, not taken.
2. **Pure value semantics; no aliasing.** Dynamic arrays are values exactly as static ones: the one-definition rule stands (rebind mints a fresh object), `Update : (ArrayDyn{T} × I × T) → ArrayDyn{T}` returns a **fresh array** (naive-copy reference semantics — heap-allocate, copy, replace slot; last-use in-place stays recorded optimization headroom per `array-scale-plan.md` 3a, unchanged in kind), all ops are effect-free and fanout-legal (E2 untouched), and no heap pointer, view, or reference ever becomes user-visible. The heap is a realization detail of the backend, not a semantic category of the language.
3. **Construction: literals stay fixed-size; dynamic arrays are built explicitly.** (a) Array literals remain `[T; N]` (Tier 0) — no implicit promotion, because implicit promotion would silently heap-allocate and silently cross the E3 boundary (the same cost-visibility norm that makes rebind require `mut`). (b) Explicit promotion builtin `vec : [T; n] → [T]` — name-resolved in lower, no grammar change (the `zip`/`print` precedent, ADR-0018). (c) `fill(x, n) → [T]` with runtime `n : i32` — the dynamic tier's natural constructor, and the dynamic twin of the static `fill` sketched in `array-scale-plan.md` W2 option 2b (one name, two tiers — naming dedupe is Open question Q4). (d) `map`/`zip`/`enumerate` over dynamic arrays produce dynamic arrays (map preserves the runtime length). **Construction-time bound:** every dynamic length satisfies `0 ≤ n ≤ i32::MAX`, checked where the length is born (`fill`, `vec`; a static literal above the bound is rejected statically, F4/SND-3 precedent) — so `len : [T] → i32` is total and `enumerate`'s `i32` index pin (ADR-0018/L1610) needs no runtime recheck. Empty arrays are legal on this tier (L1208's `n ≥ 1` remains a literal-tier rule).
4. **Bounds checks reuse the existing guard machinery — same trap kinds.** `Index`/`Update` over a dynamic array are typed exactly as today (integer scalar index; a negative index is a trap, not a type error — ADR-0021); OOB (`i < 0 ∨ i ≥ len`) ⇒ `Trapped(IndexOob)`, the existing class, no new kind. What changes is only the *source of the bound*: a runtime read of the value's length instead of the type's constant. In the LLVM emitter that is one `load` of the header feeding the unchanged `guard_index` check shape (`func.rs:608–618`); in the oracle it is `Vec::len` where today the `Ty` supplies it (`eval.rs` Index/Update arms).
5. **`zip`/`enumerate` over runtime lengths: mismatch traps.** Typing generalizes to any mix of static and dynamic operands: both-static keeps today's compile-time check (L1608); any dynamic side moves the check to runtime. **Length mismatch ⇒ `Trapped(LenMismatch)` — the language's third trap kind** (`flow_trap` kind 2, one new message row in `flow-rt/src/lib.rs:60–65`; `TrapKind` gains a variant, `value.rs:32`). R1 is unaffected: traps are ⊥-identified and exit 101 either way, so the differential equality relation does not change shape. The same kind covers a negative `fill` length (a length error, not an index error). **The named alternative is truncate-to-shorter** (the Haskell/Rust-iterator convention): rejected — it silently drops data, which is exactly the "silent acceptance" the project rejects elsewhere (ADR-0001), and it voids the categorical reading of `zip` as the iso `A^N × B^N ≅ (A×B)^N`, which holds only for equal extents.
6. **Realization: heap allocation through `flow-rt`.** Two new externs, `flow_alloc(size) -> ptr` / `flow_free(ptr)` — precisely `array-scale-plan.md` W1 option 1a's pair, thin over Rust's allocator; `flow_print_str`'s `(ptr, len)` FFI is the in-repo precedent that the seam supports this shape. **OOM is pinned to abort** (NULL ⇒ abort, matching Rust's allocation-failure behavior), *not* a `flow_trap` kind: the oracle has no OOM outcome and L1's classes never cross. Frees are inserted at the last-use frontier (category-ir §9.4/§10 — its first real consumer); an array returned from an internal fn transfers its single free duty to the caller (the caller-frees rule recorded in W1; no user-visible change, as in Core today). Nested dynamics (`[[f32]]` — the §8.4 matmul exhibit) are permitted: last-use free insertion becomes type-directed and recursive, the same walk the interpreter's value `Drop` already performs. The interpreter needs no allocator: `RValue::Array(Vec<…>)` already *is* the semantic model, and the compiled artifact is judged against it on values (L1), not on allocation traces.

## The E3 reopen — the guarantee stops being vacuous

E3/ADR-0004 scopes the memory guarantee (no use-after-free / double-free / leak / race, zero annotations) to the first-order non-cyclic core, and `flow-as-implemented.md` §5 item 3 records that the scope currently contains **zero heap operations** — the guarantee holds vacuously. This ADR puts the first heap operations into the scope. The restated guarantee, if accepted:

> For the first-order, non-cyclic core **extended with dynamic arrays**: no use-after-free, no double-free, no leak within a function body, no heap data race — because (a) every heap array has exactly one owning object at a time (one-definition rule; rebind mints a fresh object — value semantics, §Decision-2); (b) each buffer is freed exactly once, at the last-use frontier; (c) escape at return transfers the single free duty to the caller; (d) lengths are immutable, so a length can never desynchronize from its buffer; (e) no sharing exists, so no refcounting is needed and no cycle can form.

The ADR-0004 out-of-scope set (closures, channels, cyclic structures) is untouched — this is an extension of the proven region along one axis, not a claim over the full language. Two honest notes. First, the guarantee becomes *load-bearing on machinery that does not exist yet*: the free-scheduling pass is the large cell above, and without it every dynamic program leaks — so unlike W1's optional threshold lowering, **the frontier machinery is mandatory in the same increment as the type former**; there is no correct partial landing. Second, the guarantee becomes *empirically testable* for the first time: a debug alloc/free counter in `flow-rt` lets the differential harness assert balance at exit 0 — the "allocation/free trace" verification ADR-0004's consequences anticipated. On acceptance, `flow-as-implemented.md` §5 item 3 is patched from "vacuous-by-proof" to the restated guarantee and its trigger line removed.

## Relationship to ADR-0024 (size-parametric templates)

The two candidates share one design conversation — both grow the `[T; N]` family — but are separable decisions. ADR-0024's size-parametric `[A; N]` keeps `n` **in the type**: monomorphization stamps each instance to today's static IR, so it needs no heap, no runtime checks, no new trap kind, no E3 reopen (design note Tier A). This ADR removes `n` **from the type**: heap, runtime bounds, runtime length equality, the E3 reopen (Tier C). Neither depends on the other and either can land first; their interaction is confined to (a) surface spelling — `[T]` here vs. `[A; N]`-with-variable there must not collide or read as two half-notations (Q1 is therefore a joint question), and (b) `zip`/`enumerate` typing across tiers, which this ADR's any-mix rule already accommodates. What this ADR does **not** do for `vector.flow`: its `[A; N]` kernels are ADR-0024's tier; dynamic arrays alone do not make that file compile.

## Open questions for Sapir

- **Q1 — surface syntax.** `[T]` (already parsed and taught in user-guide §2.1; one P-code flips) vs. `Vec<T>` (the design note's Tier-C name; rides the P0103 generic-args form) vs. a fresh spelling (`[T; ?]`). Sub-question: user-guide §2.1 calls `[T]` a "dynamic array / **slice**" — a slice connotes a *view*, and this proposal is an owned, non-aliased value. Either the word "slice" leaves the guide, or the spelling should. Proposed lean: `[T]`, owned, no views.
- **Q2 — growable vs. fixed-but-unknown.** This candidate fixes length at creation ("growth" is allocate-new + copy, expressible in-language). Growable `push`/`reserve` would put a second runtime size (capacity) into the value and buy amortized growth at the price of the aliasing-adjacent semantics E3 currently avoids. Proposed lean: fixed-but-unknown, growth ops never — the motivating kernels do not need them. Sapir decides.
- **Q3 — the device-memory story.** Where do dynamic arrays live for F_CUDA (and TT under ADR-0025): device buffers with explicit host↔device transfer ops (new ops; possibly token-threaded), or placement decided per target (the `@device/@shared/@bram` embryo, user-guide §9.2)? This ADR proposes CPU-heap semantics only and marks placement as a joint P6-DESIGN/ADR-0025 conversation, per `array-scale-plan.md` sequencing item 3.
- **Q4 — small namings.** `fill` shared across the static (W2 option 2b) and dynamic tiers — one builtin or two? `len` as a primitive op or as a projection of the dependent pair? And the sequencing gloss: ADR-0021 records "after coproducts per HANDOFF §4.2 ordering", but HANDOFF §4.2 lists without ordering and this candidate needs no coproduct machinery (that dependency is Tier B's). Confirm the order, or record the corrected gloss.

## Non-goals (asked and answered)

- **No refcounting, no GC.** `array-scale-plan.md` 3b stays rejected-for-Core: value semantics plus frontier frees answer statically what refcounts answer dynamically.
- **No aliasing, no mutable references, no views.** Arrays remain values; the one-definition rule (ir I3, ADR-0013) and E2 are untouched; "slice-as-view" is explicitly not proposed (Q1).
- **No change to literal-size arrays.** `[T; N]` typing, semantics, allocation, and L1208/L1608/L1610 behavior are untouched; promotion to the dynamic tier is explicit only.
- **No growable ops in this ADR** (Q2); **no streams/channels** (Tier C-`Stream` is the KPN/E2 conversation, not this one); **no closures or capture** (L1108 stands); **no device-memory semantics** (Q3).

## Consequences

If accepted: user-guide §8.2/§8.4's badges flip to compilable and the language gains its first runtime-extent collection; E3 gains content and its first testable enforcement hook; the last-use frontier gains its first consumer, with the free-scheduling pass as the increment's center of gravity. Costs honestly stated: naive `Update` over dynamic arrays allocates and copies per write (the ADR-0021 correctness-first stance, now through malloc — 3a's in-place headroom grows more valuable, not less); the LLVM backend carries the only large cell; Verilog gains a permanent ✋ row; the oracle gains a third outcome variant. If rejected or deferred: nothing changes — this file records a design, P0104 stands, and the thin-ice entry keeps its trigger line.

## Acceptance amendment (2026-07-18, Sapir)

Accepted by Sapir for **post-M5** scheduling, with this amendment — the **per-backend size allocator**:

> Every backend provides its own "size allocator" — a store component that owns the storage and the allocation mechanism. On CPU it is the heap; on CUDA/TT a device memory pool; on ASIC/FPGA a static, fixed-capacity store — which may itself be a component designed in Flow. "Actually everything requires a fixed size": the heap is only the largest store. The store exposes its **failure mode** (store full / allocation impossible), and **allocation is fallible and must be handled by the calling code** — checked errors in the spirit of Rust's `Ok`/`Err`, shaped to fit Flow.

Consequences recorded:

1. **Checked errors become a language requirement — and they ride coproducts.** A fallible `alloc` must return a *sum* (`Ok(array) | Err(StoreFull)`) that callers *must* branch on; Flow has no sum types yet (P0105/P0106 stand). The **coproducts ADR is therefore a dependency of this increment**, and the exact checked-error shape is decided there, not here. (Orchestrator's proposal, for that ADR: named sums + pattern guards — the already-reserved `-Ok(x)->`/`-Err(e)->` guard syntax (P0106) over the existing Phi machinery; no exceptions, no new effects.)
2. **Two failure tiers, kept distinct.** *Traps* (`DivZero`/`IndexOob`/`LenMismatch` — bug-class, ⊥, exit 101) for programmer errors; *checked sums* for expected, environment-dependent failure (allocation; later possibly I/O). The allocator never traps on fullness — it returns `Err`.
3. **Uniform code across backends.** The same program guards every allocation; on heap backends `Err` is practically unreachable, on ASIC it fires when the store fills. The failure *mode* is semantics (portable); the failure *frequency* is target-specific (realization) — the functor thesis extended to failure handling.
4. **Q3 (device-memory story) is answered by this amendment** — the allocator/store is the answer; any placement ops ride the coproducts-AD design. Q1 / Q2 / Q4 remain open; the orchestrator's leans (`[T]` spelling, fixed-but-unknown with no growth ops, one `fill` builtin across tiers) stand as proposals for the implementing session.
