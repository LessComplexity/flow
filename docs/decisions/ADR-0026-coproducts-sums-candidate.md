# ADR-0026: Coproducts — named sum types, variant constructors, pattern guards (candidate)

Date: 2026-07-19 · Status: candidate — proposed 2026-07-19 · NOT decided · number provisional · changes nothing until accepted

## Context (what forced the decision; spec refs)

Flow's type algebra has products and lacks their dual. Tuples are "the canonical categorical product" (user-guide §2.1), named structs are nominal products (`Ty::Struct`, `flow-ir/src/ty.rs:43–46`), and the spec's first pillar already promises the missing half: "pattern-match guards are coproducts" (user-guide §1). `Ty` has no sum variant — the closed enum is `Int | Float | Bool | Unit | Str | IoToken | Tuple | Struct | Array` (`crates/flow-ir/src/ty.rs:23–52`), with the header comment recording the debt verbatim: "Omitted vs spec §3.4 (added when their feature lands): `Char`, `Never`, `Sum`, `Option`, `Result`, `Fn`, …". The language as implemented confirms the gap: "coproducts/enums/`Option`/`Result` and `?` (P0105/P0106/P0101)" do not exist in Core (`flow-as-implemented.md` §2.1).

The surface is reserved, not undesigned, and it is reserved in two exact places (verified against the parser, not the docs):

- **Declarations (P0105).** `parse_enum_variant` (`crates/flow-syntax/src/parser.rs:595–616`) recognizes `'-' IDENT` with an optional balanced `{…}` **or** `(…)` payload, keeps the `type` declaration, and rejects: "enum/coproduct variants in a `type` body are out of Flow-Core (HANDOFF §4); planned for Core+1 coproducts". This is precisely the syntax user-guide §2.1 teaches:

  ```flow
  type Shape {
      -Circle { radius: f32 }
      -Square { side: f32 }
      -Rectangle { width: f32, height: f32 }
  }
  ```

  with the note "The guard syntax (`-Variant-…`) is reused for the variants of an enum — matching the guard syntax used elsewhere for pattern matching" (user-guide §2.1), and §7.1's `type Result<T, E> { -Ok(value: T) -Err(error: E) }` ("The Result type is a coproduct").
- **Pattern guards (P0106).** A `Minus` span-adjacent to an identifier (or `[`), an optional balanced group, and a span-adjacent `Arrow` classifies as a pattern arm (`parser.rs:1006–1010`, `is_pattern_arm`), rejected at `parser.rs:2104–2126`: "pattern guard arms (`-Some(x)->`, `-[h, ...t]->`) are out of Flow-Core (HANDOFF §4); planned for Core+1 coproducts" — producing `GuardDiscr::OutOfCore` (`ast.rs:266–276`). The pinned regression test fires P0106 exactly twice on `opt -> { -Some(x)-> y; -None-> 0; }` (`parser/tests.rs:1408–1418`), so bare `-None->` and payload-carrying `-Some(x)->` are both reserved. User-guide §3.4 teaches the consumption form over this reserved syntax (`-Some(x)-> x * 2; -None-> 0;`) and states the intended semantics: "Internally, guards lower to coproduct injection and copairing" (category-ir §2.3).

The forcing function is ADR-0023's Acceptance amendment (2026-07-18, Sapir): "allocation is fallible and **must be handled by the calling code** — checked errors in the spirit of Rust's `Ok`/`Err`, shaped to fit Flow", and its recorded consequence: "A fallible `alloc` must return a *sum* (`Ok(array) | Err(StoreFull)`) that callers *must* branch on; Flow has no sum types yet (P0105/P0106 stand). The **coproducts ADR is therefore a dependency of this increment**." HANDOFF §4.2 has always carried the ordering: "coproduct/enum types, `Option/Result`, `Some(x)` patterns, and `?` (Core+1: **first feature after M2**, since coproducts are central to the categorical story)". This is that ADR, written as a candidate.

## Decision (imperative, if accepted)

1. **Named sums in `type` declarations — the reserved syntax, nothing new.** A `type` body may contain variant members in exactly the two forms P0105 already reserves: `-Variant { field: T, … }` (named-field payload, the struct mirror — §2.1's `Shape`) and `-Variant(payload: T)` (the paren form — §7.1's `-Ok(value: T)`), plus the bare `-Variant` (zero payload; the P0105 skip accepts a missing group). Semantics: the declared type is the coproduct `Variant₁(P₁) + … + Variantₖ(Pₖ)` — nominal like `Struct` (equality includes the name), **monomorphic and non-recursive** in this increment: payloads are concrete first-order Core types (no type parameters — ADR-0024's follow-on; no decl cycles through sums — the first-order non-cyclic scope of E3/ADR-0004, enforced as a named diagnostic at declaration). P0105 flips to acceptance; the token-skipping `parse_enum_variant` becomes a real parse into a new `TypeDecl` variant-member AST node.

2. **Construction — name resolution, zero parser change (verified against the reservation boundary).** The taught call shape `Ok(d)` / `Some(mid)` (user-guide §7.2, §8.5) is **not** taken as-is: it is call-expression shape, rejected P0108 at *parse* time, before any name resolution exists to know `Ok` is a variant — carving a constructor exception into P0108 would break the E4-era rule that kept the parser symbol-free. Instead constructors resolve as **names in lower, the ADR-0018 `zip`/`print` precedent**: a brace variant constructs through the existing struct-literal form (`Circle { radius: 1.0 }` parses today; lower resolves `Circle` to the variant instead of a struct); a paren variant constructs as a name **stage** consuming the wire (`payload -> Ok -> ret;`); a zero-payload variant is a bare name expression (`None -> ret;`). Whether the taught call shape is later recovered (a P0108 constructor exception) is Open question Q2. Lowering: one new IR op `Inject { variant } : Pᵢ → S`.

3. **Consumption — pattern guards over the existing Phi machinery; exhaustiveness is the enforcement.** A guard block over a sum scrutinee takes arms `-Variant(x)->` (binding `x : Pᵢ` for the arm payload only) or `-Variant->`; the discriminant family `GuardDiscr` gains the variant case where today `OutOfCore` stands. Lowering **desugars n-ary to nested binary exactly as `emit_value_match` already does for integer guards** (`crates/flow-lower/src/emit.rs:1867–1971`): per arm a condition op `IsVariant { variant } : S → Bool`, then the right-fold of `Phi : (T × T × Bool) → T` with the default arm innermost — the same shape, the same merges, no n-ary IR node. **A guard over a sum must cover every variant of the declared type, or supply `-_->` for the residue** (the two existing disciplines composed: bool guards' pole-or-default rule, L1401, and value-match's mandatory default; an all-variants guard plus a default is the unreachable-arm case, L1402). A guard that misses variants **and** has no default is a named diagnostic in the L1401/L1402 family, naming the uncovered variants. This is what makes "must handle" constructional rather than lint-level: **a sum value is opaque except through guards** — there is no surface projection out of a sum (member access on a sum is a type error), the IR's payload projection is emitted only inside the arm it belongs to, and every variant must be answered. Bool is the two-variant special case already implemented: `-true->`/`-false->` over `Ty::Bool` is today's guard; whether Bool *formally* unifies into the sum machinery is Open question Q4 (v1 keeps it special — zero delta to the existing path, `emit.rs:1762–1865`).

4. **Realization — strict select stands; payload reads are totalized (the verification finding).** The desugar was checked against the four guard consumers, and it holds **only with a precise payload rule**, because Phi is strict: the interp reads both precomputed arm values and picks one (`flow-interp/src/eval.rs:188–198`); llvm emits one `select` over both loaded arms (`flow-backend-llvm/src/func.rs:348–355`); the CUDA DESIGN pins "strict select: both arms computed into temporaries, then `cond ? t : f` … (a C++ ternary *over expressions* would skip the untaken arm's trap)". Two naive rules fail. (a) *Wrong-variant payload read traps*: impossible — under strict evaluation every arm computes, so every guard would trap on every non-matching variant. (b) *Wrong-variant read reinterprets the stored bits*: the interp's `RValue` is not a bit union (`value.rs:12–28` — a payload is one typed value), and llvm garbage bits make an unselected arm's trap (`1 / x`) fire nondeterministically — oracle and compiled artifact diverge, an R1 violation by construction. **The rule: `Payload { variant } : S → Pᵢ` is total — on a non-matching tag it yields the canonical zero of `Pᵢ`**, realized identically on every target (`select(tag == i, payloadᵢ, zero)` in emitted code; the oracle manufactures the same zero). `zero(T)` is total, terminating (v1 sums are non-recursive), and non-allocating: scalars → 0/false, tuples/structs/fixed arrays → componentwise, `Unit` → `Unit`. The unselected arm's value is thereby defined, deterministic, and discarded by the Phi — and arms inherit today's documented strict discipline verbatim: an arm must be total for *every* payload value including the zero, exactly as today's arm must be total for every scrutinee value (`1 / 0` in an unselected bool arm traps today — `flow-as-implemented.md` §2.4, not new sharpness). v1 sum guards are **Phi-position only**: routing-position sum guards (jump arms) stay in the L1409 designed-out class with integer-discriminant routing, and the Phi-arm restrictions stand unchanged — pure arms (L1404), no `-> ret` (L1405), no enclosing-`mut` assignment (L1408).

5. **Monomorphic first; the compiler's checked operations use primitive builtin sum formers.** User-declared sums are concrete. The allocator contract of ADR-0023's amendment does **not** wait for generics: the store's result is a **primitive built-in sum former** resolved by name in lower — the `print`/`zip` precedent (ADR-0018) — exposing `alloc`/`fill`/`vec` results as `Ok(array) | Err(StoreFull)` over a compiler-known sum type, guarded by the same machinery as user sums. Generic user sums (`type Result<T, E>`) are ADR-0024's follow-on — templates stamp monomorphic instances with **zero IR change**, which composes cleanly with this ADR's closed `Ty`; that deferral is Open question Q5.

6. **The two-tier failure discipline, stated as law.** *Traps* (⊥, exit 101: `DivZero`/`IndexOob`/`LenMismatch`) are for programmer errors; *checked sums* are for expected, environment-dependent failure (allocation; later I/O). **Only explicit constructors are checked** — `fill`, `vec`, `alloc`, the morphisms that summon values from the environment. Structural dataflow over values already in hand — `map`, `zip`, `enumerate`, `Update`, arithmetic, guards — keeps trap/infra semantics. The composition rule, as law: **fallibility attaches to construction, never to transformation**; a value, once held, is total to transform. This line is the ergonomics safeguard — it is what keeps ordinary pipelines free of `Ok`-unwrapping — and it is what keeps the checked tier from leaking across the language: no operation gains a sum result unless this ADR or a later one names it.

7. **Per-backend store semantics; the Err arm is testable.** The amendment's allocator lands per backend: CPU heap (`Err` practically unreachable — still guarded, same code), CUDA device pool (P6 DESIGN), TT DRAM (ADR-0025, P8), ASIC/FPGA a static fixed-capacity store — which may itself be a component authored in Flow (a bump allocator is an index plus a fixed array). The failure **mode** is portable semantics; the failure **frequency** is target-specific realization. Testability: the harness pins the store capacity identically in oracle and backend test builds (small capacities make `Err` reachable), so the differential duty (ADR-0020) covers both arms on every target; production capacities stay target-specific. No new trap kind: `StoreFull` is *data* — an `Err` payload — not a `flow_trap` row.

8. **Effects and the trap tiers untouched.** Sums are pure values: E2/ADR-0003 is untouched, no token law changes (a token cannot reach a payload — surface types cannot name `io`, and the shared `ty_contains_token`/`ty_contains_str` walks gain one arm each so every existing invariant sees through sums, `ty.rs:208–264`; `TokenInPhi` applies to sum-typed selections unchanged). E1's `B ⊕ U` in the loop step (`flow-as-implemented.md` §2.5) is noted as semantics-level precedent that coproducts already structure the language's meaning — it is not a user type and becomes no more user-visible than today.

## Open questions for Sapir

- **Q1 — declaration spelling.** Keep both reserved payload forms (brace `-Circle { radius: f32 }` and paren `-Ok(value: T)`) plus bare `-None`, or prune to one? Sub-question: variant names are program-global (single file, P0112) — acceptable, or must they be type-qualified (`Shape.Circle`)? Proposed lean: both forms, global names.
- **Q2 — construction surface.** Confirm the zero-parser-change design (struct literal + name stage; §Decision-2), or carve a variant-constructor exception into P0108 to recover the taught `Ok(d)` call shape (cost: the parser's symbol-free, E4-era rule gains a hole, or rejection must defer to lower). Proposed lean: zero-parser-change; user-guide §7.2/§8.5's call-shape examples get a living-correction marker on acceptance.
- **Q3 — exhaustiveness discipline.** Cover-all-variants-or-default (this candidate's rule) vs mandatory default (value-match discipline) vs default forbidden for sums (maximal enforcement). Note the load-bearing consequence of the chosen rule: under this candidate, *adding a variant later breaks every all-explicit guard* — the intended "must handle" tripwire — while guards with `-_->` keep compiling. Sapir picks; the orchestrator leans as written.
- **Q4 — Bool.** Does `Bool` formally unify into the sum machinery (a builtin two-variant sum, guards desugared uniformly), or stay a primitive special case? Proposed lean: stays special in v1 — the two-arm Phi over `Ty::Bool` *is* the copairing already; unification is a later cosmetic refactor with zero user-visible content.
- **Q5 — generics deferral.** Confirm generic sums (`type Result<T, E>`) ride ADR-0024's monomorphization and are not this ADR's business. (ADR-0024 is itself a candidate; the deferral is consistent with its zero-IR-change design.)
- **Q6 — the `?` shorthand.** Does the reserved propagation operator (P0101, precedence already pinned at user-guide §3.6 row 9) ever get its own ADR — presumably after this one and ADR-0023 land, as sugar over the guards defined here? Proposed lean: yes, its own ADR; not this one.
- **Q7 — n-ary guards.** Stay sugar (this candidate: the `emit_value_match` precedent — the binary Phi is the IR's honest copairing) or become a first-class n-ary IR node? Proposed lean: sugar.
- **Q8 — strict vs honest coproducts (the design fork).** This candidate keeps strict select + totalized zero payload reads (§Decision-4). The alternative is the honest-coproduct lowering (lazy arm cones, category-ir §4.6 — the machinery L1404 defers), which would also unlock effectful arms and remove the strict-trap landmine, at the price of non-strict conditional machinery the IR does not have (loops' decide/advance cones are the only non-strict conditional today, and they are SCC-scoped, ADR-0016). Proposed lean: strict for this increment; §4.6 stays its own ADR.
- **Q9 — tag representation.** `IsVariant { variant } : S → Bool` (one op, this candidate) vs `Tag : S → I` + existing `Eq` against constants (fewer ops, more nodes). Dedupe at implementation.

## Non-goals (asked and answered)

- **No exceptions, no effects.** The failure tier is *values*, not control effects; E2 and the token laws are untouched; effectful arms stay L1404-rejected (the §4.6 honest-coproduct lowering is its own ADR — Q8). Checked-error handling in v1 is by *values*: fallback, or returning the sum to the caller (a function may return a sum — `ret` is an ordinary target outside Phi arms).
- **No deep or nested patterns in v1.** A pattern arm is `-Variant(x)->` or `-Variant->` — one flat binding; fields are then reached with ordinary member access (`x.radius`). Nested patterns (`-Some(Ok(x))->`) and the array patterns (`-[]->`, `-[h, ...tail]->`) stay reserved for their own ADRs.
- **No generic sums** (ADR-0024 — Q5); **no `?` propagation operator** (its own future ADR — Q6); **no change to the trap tiers** (no new trap kind; §Decision-7); **no modules** (variant names are program-global — Q1).
- **No recursive sums in v1.** A declaration cycle through a sum is a named diagnostic; tree types need the heap/cycle story and are their own ADR (E3 scope).
- **No routing-position sum guards.** Sum guards are pure, value-producing Phi position only; jump-arm routing over sums stays in the L1409 class.

## Consequences

If accepted: the type algebra gains its missing dual; P0105/P0106 flip; user-guide §2.1/§3.4's badges flip to compilable (§7.1 partially — the *sum machinery* becomes real, the *generic* `Result<T, E>` still awaits ADR-0024); ADR-0023's allocator amendment unblocks — checked allocation errors land on the machinery defined here, post-M5 as scheduled; the oracle gains a new value shape and the differential duty gains the wrong-variant-zero obligation (§Decision-4). **Costs stated plainly: this is the biggest Core change since ADR-0013.** Unlike ADR-0024's templates (zero IR change — stamping to today's IR) and unlike ADR-0021's single op, `Ty::Sum` is a new variant of the type algebra itself: every closed `Ty` match in every component gains an arm, and every backend — including the two unbuilt ones' DESIGNs — gains a type realization. The strict-select payload rule (§Decision-4) is a real semantic pin with a real sharp edge (arms must be total on the canonical zero, exactly as they must already be total on every scrutinee value), adopted because the honest-coproduct alternative needs non-strict machinery the IR does not have (Q8). Lower carries the center of gravity; llvm is the only backend with real emission work this increment; the tag-directed free walk is recorded joint scope with ADR-0023's heap pass. If rejected or deferred: nothing changes — this file records a design, P0105/P0106 stand, and ADR-0023's increment stays blocked on its recorded dependency.
