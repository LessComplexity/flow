# ADR-0025: TT backend — a third functor target via TT-Metalium emission (candidate)

Date: 2026-07-18 · Status: **accepted — decided by Sapir 2026-07-18 (S14): the P8 target, strictly post-M5; Blackhole is the chosen architecture generation.** Q1 answered as proposed (TT-Metalium emission; the §2 revisit triggers stand); Q2 answered (Blackhole hardware is Sapir's on-metal target; ttsim still carries CI); Q3 (whether TT becomes the O5 vendor-pitch demo) left open. Number final: ADR-0025.

## Context (what forces the proposal; spec refs)

`category-ir.md §8` defines a backend as a functor `F : Flow-Cat → T`; ADR-0020 fixed the shared emission contract (`emit(ir) -> Result<String, EmitError>`, one `flow-rt`, oracle-parity semantics, per-backend differential duty) before the first backend was written. The functor-backend thesis is thereby an _empirical_ claim, and its evidence base has a shape problem. After M5 the portability argument rests on F_LLVM (P5, implemented: `flow-backend-llvm`, ~1.3k lines) and F_CUDA (P6, at the DESIGN gate this session) — two points in **one programming-model family**: cached memory, thread-per-element work distribution, sequential host toolchain. F_Verilog (P7) adds a second family but simulation-only and capability-narrow (HANDOFF §8: feedforward pipelines + single-loop FSM). The uncovered quadrant is the one VISION's O5 actually sells: **commercial spatial manycore with an explicit memory hierarchy** — no caches, explicit buffers, tile-native compute. If the functor story only ever lands on CUDA-like hosted targets, "a vendor writes one backend and inherits the ecosystem" (VISION §1, O5) remains an inference from evidence gathered inside a single model. A third, non-CUDA-like target is what turns the one-pair observation into a claim about the architecture.

TT is the concrete O5 beachhead candidate: a real vendor with purchasable silicon (Blackhole p100a / Wormhole n150s ≈ $999), a bit-exact simulator (ttsim) that runs CI without hardware, an open low-level stack, and independent third-party precedents that the hardware is targetable off the official ML path (triton-TT, tt-iree, zyx; official path: tt-xla). VISION §7 sequences O5 strictly after M5; this candidate proposes no schedule change. It exists so the post-M5 slot (a P8 candidate) has a worked design on file if Sapir accepts it. Until then it binds nothing.

## Proposed decision (inert until accepted)

1. **Fourth functor: `F_TT : Flow-Cat → TT-Cat`, one more `emit()` crate.** `crates/flow-backend-tt` exposing the ADR-0020 signature; the `String` is one C++ translation unit (host + reader/compute/writer kernels) piped to the host `clang++` against the Metalium SDK — the emit-to-text-then-external-toolchain shape ADR-0020 already mandates. Zero IR change, zero new ops, zero new trap kinds.

2. **Emission path: TT-Metalium host+kernel C++, not TTIR/tt-mlir.** Metalium is the stable contract: apt-installable, version-pinnable, a plain C++ surface that emit-to-text reaches directly — the LLVM backend's toolchain-pipe shape transfers unchanged. The TTIR path is architecturally purer (Flow as a proper MLIR-dialect emitter, inheriting vendor scheduling work) but tt-mlir churns monthly: pinning Flow's oracle-parity differential suite to a monthly-moving dialect risks CI going red on vendor upgrade rather than on a Flow bug, and "toolchain absent ⇒ skip-with-reason" (HANDOFF §5.5) is a poor answer when the toolchain is present but shifted. **The named trade-off:** Metalium buys stability at the price of owning tile/CB/NoC scheduling by hand — VISION §5 truth #1's per-target performance work, here with no MLIR pass infrastructure between Flow and silicon. TTIR would rent that infrastructure at the price of importing vendor churn into Flow's correctness story. **Revisit triggers:** a tt-mlir stability commitment (versioned dialect, deprecation policy), or a second MLIR consumer inside Flow making the investment pay. tt-lang is noted and rejected as an emission target: it is a Python DSL, Flow emits C++ text, and routing through a Python front-end adds a toolchain tier for no semantic gain; its hardware-free-simulator idea is already covered by ttsim.

1. **Traps: predicate + host-validate.** A kernel cannot `exit(101)`; there is no on-device trap. Every may-trap op (`Div`/`Mod`/`Index`/`Update`) writes a trap-kind word to a device trap-flag buffer on the failing lane instead of trapping. The host reads the flag at every workload completion — synchronization points the mapping already requires (prints, loop guards, fold staging) — and calls `flow_trap(kind)` host-side **before the next observable effect**. Parity argument: ADR-0020 §3 defines `Trapped(_)` ⟺ exit 101 with stdout ignored on trapping runs, and rewrite R1 ⊥-identifies trap classes; don't-care lane values on a trapping run are unobservable, so host-surfaced exit 101 is oracle-equal by construction. Cost named: one device buffer plus one readback per sync point.

2. **Differential duty: ttsim in CI, one card on metal.** (a) ttsim (bit-exact) carries the full ADR-0020 §4 duty — all `examples/*.flow` + testgen programs, raw and rewritten — per-commit, no silicon required; toolchain absent ⇒ `#[ignore]`-with-reason recorded in the component STATUS, never a faked pass. (b) One Blackhole p100a / Wormhole n150s (≈ $999) runs the same suite on metal at release cadence; TT Cloud / Koyeb / dstack rentals are the interim. (c) **Byte-exact stdout vs tile padding — must be solved, and is solved by construction:** padding is internal-only. Every device→host readback goes through the logical-length view (`n · sizeof(elem)`), never the tile count; pad lanes are never observed and `flow_print_*` formats exactly what the oracle printed. The invariant is exercised by testgen programs with `n ≢ 0 (mod 1024)`; a padding leak would surface first as an R1 stdout mismatch, which is exactly what the readback-path discipline precludes.

3. **Capability-matrix rows from birth.** The Tensix SFPU is 32-wide fp32 and the integer datapath is 32-bit; Flow Core also admits `f64` and `i64` (`flow-ir/src/ty.rs:23`). v1 rejects device-staged `f64`/`i64` ops with `Unsupported { feature, loc }` — the ADR-0020 ✋ cell, naming the matrix row — rather than emulating silently. A host-staged fallback is later optimization, not v1. Cost against the current suite: zero — no `examples/*.flow` program uses f64/i64/u8 (verified 2026-07-18).

### Categorical model note (ADR-0022 D2 local payment)

Objects: scalars map to host/L1-resident values; `[T; n]` maps to a tilized DRAM buffer with the logical `n` carried beside the padded allocation — padding is part of the _image_, invisible to the source. Morphisms: the table in §3; composition is honored because stages compose through buffers whose contents are defined by the op images alone. Trace: unlike F_Verilog (E1 — iteration trace into a guarded trace, a theorem with content), F_TT realizes `Tr^U` as the **host's own iteration**, which carries the same least-fixpoint/Elgot semantics as the source trace — "F commutes with Tr" is near-free here, and the content moves to the trap-flag and readback protocol (§4), which is where this backend's correctness argument actually lives. Same shape as F_CUDA (§8.2): the functor laws are never the hard part; the boundary protocol is.

## Effort and sequencing

Estimate: **2–4× the P6 CUDA backend scope** — stated against a _plan_, not a measurement: P6 is at the DESIGN gate this session and has no measured baseline; the only implemented anchor is `flow-backend-llvm` at ~1.3k lines. The multiplier lands entirely in the programming model — explicit circular buffers, no caches, no `threadIdx`, tilization, host-staged control flow, the trap-flag protocol — and none in Flow: no IR change, no new ops, no spec impact; the deliverable is one more `emit()` crate plus harness rows. Sequencing: **strictly after M5** (VISION §7 sequences O5 post-M5); the P8 slot is its natural home. Starting earlier would fork the differential harness while P6/P7 are still landing on it.

## Consequences (if accepted)

The workspace gains `crates/flow-backend-tt`; the capability matrix gains a column (the f64/i64-on-device ✋ rows from §6 exist from birth — recorded, not apologized for); the docs tree gains `docs/components/backend-tt/`. The functor-backend thesis gains a third programming-model family of evidence, and the O5 pitch stops being an inference from CUDA-likes. Costs: a version-pinned Metalium SDK dependency in CI; one hardware purchase or recurring cloud spend (Open question 2); permanent ownership of tile/CB/NoC scheduling — the §2 trade-off. If Sapir vetoes, nothing happens: candidate status changes nothing until accepted, and no file outside `docs/decisions/` records this proposal.

## Open questions (for Sapir)

1. **TTIR vs Metalium long-term.** Accept Metalium now with the §2 revisit triggers, or invest in TTIR from the start to stand as an MLIR-ecosystem peer? This candidate recommends Metalium; the trade-off is recorded, not hidden.
2. **Hardware purchase vs cloud.** One ≈ $999 card (owned; on-metal runs at will) vs TT Cloud / Koyeb / dstack rentals (no capex; per-run cost, queueing). ttsim makes either optional for CI — the question is only on-metal validation cadence.
3. **Is TT the O5 vendor-pitch demo?** VISION §7 makes O5 the post-M5 expansion play and §9 asks what minimum ecosystem makes the O5 pitch credible. If this backend is also a _market artifact_, its DoD changes (a sepia-class workload running on metal, demo polish) versus a pure matrix-coverage DoD. That call is Sapir's, not this ADR's.

## Non-goals (asked and answered)

- **No ML workloads.** VISION §7: O6 is approached only via streaming/irregular dataflow, never dense GEMM; TT-NN's matmul/conv shape is out entirely.
- **No TT-NN op-library dependence.** Emission targets Metalium primitives only; linking vendor op libraries would make vendor library semantics part of Flow's oracle-parity claim.
- **No cross-core reductions in v1.** `Fold` is in-order host-staged; NoC reduce and the whitelisted tree-reduce are recorded headroom.
- **No performance claims.** v1's DoD is oracle parity on ttsim plus on-metal, full stop — VISION §5 truth #1 (performance lives per-backend and is real work) applies in full.
- **No IR, spec, or semantics change**; no new trap kinds; no dependency on candidate ADR-0023 — padding is compile-time under E3 either way.
