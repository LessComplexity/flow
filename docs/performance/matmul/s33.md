# S33 (2026-07-26) — the timed-window boundary fixed, Flow at OpenBLAS parity on AVX2, and a pool race that invalidates every `par` minimum

Two machines, run in full: **M4 Pro** (10 P + 4 E, NEON, clang 22.1.8, numpy → Accelerate/**AMX**)
and **i9-14900F** (8 P + 16 E, AVX2, gcc 15.2 / rustc 1.90, numpy → **scipy-openblas 0.3.30**,
`perf` works). Every table is one machine; cross-machine rows are labelled and never mixed into a
verdict.

Method: min-of-N of each program's own `iter ms` (the `time` builtin / baselines' self-timed
iteration), compute-only on both sides. **1t legs pinned** (`taskset -c 2` on the i9 — hybrid CPU,
unpinned readings are worthless); par/mt legs unpinned so Flow and the baselines get identical
treatment. numpy in every table (standing directive). i9 tables carry **min and median** because
of §5.

---

## 1. Headline

1. **conv2d's "1.55× per-core gap" was a measurement boundary, not a kernel defect.** Fixed;
   conv2d now **beats** naive C++ per core on both architectures. §2, §3.
2. **On hardware without a matrix coprocessor, Flow's *generated* GEMM reaches parity with
   hand-tuned OpenBLAS.** Single-threaded a flat **1.20× behind** at 1024/2048/4096; threaded
   **within ±10%** from 1024 up (ahead at 2048, behind at 512 and 4096). The M4's "numpy wins
   matmul by 3.4×" is the AMX coprocessor, now measured rather than argued. §4.
3. **A pre-existing pool race makes every `par` *minimum* unsound**, and it inverts the standing
   "quote min, never median" rule. P0. §5.

## 2. What shipped: `reside` (plan-s33)

`flow_rt_alloc` returned a reserved address range, not memory. A large `alloc` is served by
`mmap`, which delivers **no** physical pages — only a promise that touching the range produces
zeroed ones. The emitter allocates in the entry-block prologue but the tasks store later, so the
first store to each page trapped into the kernel (2 MiB of zeroing apiece under THP) *wherever
that store happened to be* — including inside a `() -> time` bracket.

conv2d exposed it because **nothing writes the output array until the convolution itself does**.
The C++ baseline never pays it inside its window: `std::vector<float> out(n)` value-initialises
and pre-faults everything before `run_iters`.

`reside` writes one byte per 4 KiB after each `alloc`. Not a memset — the fault's own zeroing *is*
the initialisation. **No emitter change, no flow-ir change, no `.ll` moved.** Diagnosis:
[`../conv2d-per-core-gap.md`](../conv2d-per-core-gap.md).

**It is not a speedup.** Total process wall time is unchanged (i9: 1.485 → 1.498 ms, +0.9% — the
~4k extra stores). It moves a real cost out of a window that was never meant to contain it.

### The counters that proved it before the fix existed

i9, exact `perf stat` counts, kernel isolated by differencing (flow: full minus a gen-only build;
cpp: `iters=200` minus `iters=1`, ÷199), warm, pinned:

| leg | cycles | **ref-cycles** | instructions | **IPC** |
| --- | ---: | ---: | ---: | ---: |
| flow `task7` | 905,100 | **299,221** | 2,034,188 | **2.25** |
| cpp `conv_range` | 1,072,928 | **382,489** | 1,914,675 | **1.78** |

`ref-cycles` ticks at the fixed TSC rate (2.0 GHz here) — frequency-invariant real time. It
validates against C++: 382,489 → **0.191 ms** vs its self-timed 0.194, so the C++ window is 98%
kernel. The same conversion put Flow's kernel at **0.150 ms** against a 0.258 ms window; the fix
landed the window at **0.144 ms**. Two independent methods, 4% apart.

**The recorded "IPC 3.11 vs 1.57" was process-level, not kernel.** Flow's generation legs
(IPC 0.86–1.04) drag its process average down, and the two programs' generation phases are not
comparable (cpp scalar ~18.7M instructions vs flow vectorised ~2.5M). Per kernel the ordering
reverses. Never quote process IPC for a kernel claim.

### What the fix is actually worth — alternating A/B, same machine, same session

The only sound way to measure it: PRE and POST built from the same `.ll`, linked against runtimes
from `HEAD~1` and `HEAD`, **alternated every iteration** so thermal drift cannot bias one leg.
min-of-9, `FLOW_PAR=1`.

| bench | M4 PRE | M4 POST | M4 | i9 PRE | i9 POST | i9 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| conv2d 512 | 0.1079 | **0.0571** | **1.89×** | 0.0370 | 0.0372 | **1.00×** |
| conv2d 1024 | 0.4389 | **0.2553** | **1.72×** | 0.2169 | **0.1610** | **1.35×** |
| fir 65 536 | 0.1323 | 0.1127 | 1.17× | 0.1151 | **0.0849** | **1.36×** |
| fir 1M | 1.7627 | 1.5767 | 1.12× | 1.4537 | 1.3516 | 1.08× |
| matmul 512 | 2.5551 | 2.3534 | 1.09× | 1.9819 | 1.7750 | 1.12× |
| matmul 1024 | 19.5682 | 19.1862 | 1.02× | 15.2878 | 14.7250 | 1.04× |
| matmul 2048 | — | — | — | 118.9342 | 117.5013 | 1.01× |
| matmul 4096 | — | — | — | 943.5674 | 940.4718 | **1.003×** |

The effect scales as *output size ÷ kernel length*, and matmul's four sizes trace it cleanly to
nothing: **1.12 → 1.04 → 1.01 → 1.003×**. conv2d is the large case because its kernel is shortest
relative to its output.

**It is platform-dependent, and conv2d 512 shows why.** 1.89× on the M4, **exactly nothing** on the
i9. macOS uses 16 KiB pages, so conv2d 512's 1 MB output faults ~64 times independently. Linux has
THP `always`, and a 1 MB array inside a 16.8 MB frame lands *inside a 2 MiB huge page its
neighbouring arrays already faulted in* — so there is nothing left for the kernel to pay. The
larger the output relative to a huge page, the more the fix matters: conv2d 1024's 4 MB output
cannot hide inside one, and there the i9 gains 1.35×. **Page size and allocation layout, not the
kernel, decide the size of this effect.**

> **Correction to an earlier claim in this session.** I first reported fir_65536 as a "2.07×
> correction" by comparing today's run against S28's recorded 0.2156. That was cross-session
> baseline drift — the exact error §6.6 warns about, committed one message after writing the
> warning. The A/B above is the truth: fir is **1.12–1.17×**, not 2×.

### The AMX result — and the honest size-by-size picture

**The 3.4× "NumPy wins matmul" gap on the M4 is hardware, not software.** That is the result. But

Flow holds **146 GFLOP/s** at all three sizes, OpenBLAS holds **174**. Neither degrades, so this

Lake. It retires the S28 "OpenBLAS frontier" item (recorded then as threaded 9.7×/5.9× ahead on

### Why threaded closes what 1t does not — tested, and it is NOT a better scheduler

Scaling 1t → 32 threads: Flow **9.8×** at 1024 and **9.2×** at 2048; OpenBLAS **8.1×** and
**7.1×**. The obvious reading — "our scheduler is better" — is **wrong**, and a controlled
experiment on this same box says so.

Same machine, same binaries, **8 threads in every cell**; only the *uniformity* of the 8 CPUs
changes. cpu 0–15 are P-core threads (5.5–5.8 GHz, two per core), cpu 16–31 are E-cores
(4.3 GHz, one each). matmul 1024² f32, median of 9, `loadavg 0.01`:

| core set (8 threads) | flow | numpy | flow/numpy |
| --- | ---: | ---: | ---: |
| **A** uniform — 8 E-cores (`16-23`) | 5.8939 | 5.5907 | **1.054** — numpy ahead |
| **B** uniform — 8 P-cores (`0,2,4,6,8,10,12,14`) | 2.4375 | 1.7242 | **1.414** — numpy ahead |
| **C** hybrid — 4 P + 4 E (`0,2,4,6,16,17,18,19`) | 3.3843 | 5.5725 | **0.607** — flow 1.65× ahead |

**On uniform cores OpenBLAS wins — by 5% on E-cores and 41% on P-cores. Flow wins only when the
cores are mixed.**

The mechanism is visible in numpy's own column: **5.5907 on 8 E-cores → 5.5725 on 4 P + 4 E.**
Replacing four E-cores with four cores 35% faster bought OpenBLAS **nothing** — static
partitioning makes every panel wait on the slowest thread, so 4P+4E performs exactly like 8E.
Flow went 5.8939 → 3.3843 across the same change, a **1.74× gain**, because work stealing lets the
fast cores absorb the slack.

**Conclusion: what Flow has is heterogeneity tolerance, not a better scheduler.** The full-machine
result (tie at 1024, ahead at 2048) exists because 16 of that machine's 32 threads are E-cores. On
homogeneous hardware — which is what a server EPYC or Xeon is — the honest expectation is that
OpenBLAS is ahead both single- and multi-threaded, and set B is the estimate: ~1.4× at 8 threads.

Consistent with this, OpenBLAS's full-machine scaling is **non-monotonic**: 1024² f32 at 8 threads
is **1.703 ms** but at 16 threads **2.441 ms** — worse with twice the threads, which is what static
partitioning across P and E cores looks like from the outside.

This is a real strength, just a narrower one than the raw numbers suggested: consumer CPUs are
overwhelmingly hybrid now (every Intel client part since Alder Lake, Apple silicon, most ARM
big.LITTLE), and on those Flow's dispatch extracts throughput a statically-partitioned BLAS cannot.
It is not a claim about beating BLAS on a server.

### Confound checked: OpenBLAS does use all 32 threads

A threaded win would be hollow if OpenBLAS self-limited. It does not — 1024² f32, default
**1.5036** vs `OPENBLAS_NUM_THREADS=32` **1.5055**. Identical. Both sides use the whole machine.
(`OMP_NUM_THREADS=1` does correctly pin it to one thread: 12.22 ms.)

Caveat kept attached: OpenBLAS is `DYNAMIC_ARCH`, so it selected an AVX2 kernel — correct for this
part, since Raptor Lake has no AVX-512, but not hand-picked for it.

## 5. ⚠ P0 — a pool race makes every `par` minimum invalid

`fir:65536 flow-fma-par` came back as **0.000417 ms**. Four tenths of a microsecond for a 65 536-lane,
64-tap FIR is impossible.

**Not the emitter.** The `time` fencing is correct — S29's fix works:

```llvm
flow_par_launch
flow_par_wait(%h, @ckpt0_entries, i32 5)   ; the generation tasks
%t0 = call double @flow_time_ms()          ; t0
flow_par_wait(%h, @ckpt1_entries, i32 7)   ; adds task6, task7 — the kernel
%t2 = call double @flow_time_ms()          ; t1
```

**The pool.** `flow_par_wait` is *help-first*: the waiting host executes any available work,
**including tasks beyond the watermark it is waiting on**. When the host steals `task7` slices
during the *first* wait, the kernel finishes before `t0` is read and the second wait returns
instantly.

### Incidence — fir 65 536, 100 runs per cell, readings under 0.01 ms

| width | bogus | median | min |
| --- | ---: | ---: | ---: |
| `FLOW_PAR=1` | **0/100** | 0.0908 | 0.0902 |
| `FLOW_PAR=2` | 0/100 | 0.0590 | 0.0510 |
| `FLOW_PAR=4` | 1/100 | **0.0382** | 0.0043 ✗ |
| `FLOW_PAR=8` | 0/100 | 0.0490 | 0.0172 ✗ |
| `FLOW_PAR=14` | 4/100 | 0.0562 | 0.000125 ✗ |

`conv2d_512` par: 4/100. **`FLOW_PAR=1`: 0/100** — no workers, nothing can run ahead. That is why
every 1t table here is trustworthy and every par cell is quoted as a median.

It also turned up live on the i9 during the width sweep, in the cell that matters most:
matmul 1024² f32 at `FLOW_PAR=32` returned **min 0.0001 ms, median 1.5259**. Had that minimum been
taken at face value it would have read as a 15,000× speedup over one thread.

### It predates `reside`

Same bench, same 100-run protocol, against a runtime built from `HEAD~1` in a worktree:
**PRE 3/100, POST 3/100.** Identical. `reside` neither caused nor worsened it.

### It inverts "quote min, never median"

That rule (S31 §4) came from **frequency ramp**, which makes **slow** outliers — so min is robust.
This race makes **fast** outliers, so min is *maximally* vulnerable, and it worsens with N: at
3–4% incidence min-of-7 is poisoned ~22% of the time and min-of-100 essentially always.

**Corrected rule: min for `1t`, median for `par`, until the pool is fixed.**

Consequences: every `par` minimum in S28–S32 is suspect (min-of-3 ⟹ ~10% risk per cell, with no
way to tell sound cells from corrupted ones after the fact), and **the S32 scheduling result
(1.41–1.43×) needs re-confirming under a median.** The fix belongs in `flow_par_wait`: help only
with work at or below the watermark being waited on.

## 6. Method notes

1. **Pin, always.** Twice this session an unpinned reading produced a confident wrong conclusion
   on the hybrid i9: a "2.2× g++-vs-clang baseline spread" that vanished under `taskset` (0.2077
   vs 0.2191 — no spread at all), and a "2.37× cold vs 1.12× warm" ratio from single runs that
   min-of-40 refuted (1.56× / 1.33×).
2. **`ref-cycles` separates frequency from time.** `cycles` alone cannot distinguish a slower
   clock from more work.
3. **Cross-validate sampled against exact.** Sampled per-symbol instructions came out 2,034,967
   vs exact 2,034,188 — 0.04%. That agreement licensed trusting the rest.
4. **`cargo test` does not rebuild `target/release/libflow_rt.a`** — only the rlib. The first M4
   measurement of the fix linked the stale runtime and read "no change at all." Run
   `cargo build -p flow-rt --release` before any hand-linked leg. **A stale staticlib presents
   exactly as a fix that does nothing.**
5. **`calloc` is not a pre-fault.** An early probe used `calloc`/`malloc` and appeared to refute
   the whole diagnosis: `calloc` on a 4 MB request returns a fresh mapping whose pages are still
   untouched, so both arms faulted inside the window — and glibc's region was not 2 MiB-aligned,
   so it took ~1024 small faults instead of 3 huge ones (0.52 ms vs 0.21). Only `std::vector`'s
   value-initialisation actually pre-faults. **Page size is decided by alignment, not by request
   size.**
6. **Baselines drift across sessions; ratios within one run do not.** cpp-1t fir 65 536 reads
   1.3024 here against S28's 0.9239 — a 41% swing in the *baseline*, from machine state alone.
   This is why the index rule is "compare within one session file, never across," and why the
   fix's effect is measured by the alternating A/B in §2 rather than against recorded history. I
   violated this rule myself once this session; the correction is recorded there.
7. **numpy has no threaded leg for the shapes because no threaded kernel exists** — `fir` is
   `np.correlate` (single-threaded C; `OPENBLAS_NUM_THREADS` is irrelevant) and `conv2d` is a
   Python loop over nine `out += w[k]*slice` passes, i.e. 9 reads + 9 writes of 4 MB, memory-bound.
   Stronger and more accurate than "the harness does not run one." matmul *does* have a threaded
   numpy leg, and the harness's `OMP_NUM_THREADS=1` does correctly limit scipy-openblas (12.18 ms
   vs 1.50 threaded at 1024²) — verified, because it was not obvious that a veclib-oriented env
   would bind OpenBLAS.
