Host CPU: AMD EPYC 9B14 (container sees 384 host threads; instance quota ≈ 48 cores — chapel's qthreads and flow's scheduler both spawn against the same visibility, so within-table ratios are like-for-like).

The `-1t` rows are the SAME binaries pinned to one thread — the single-thread baseline inside the same table. chapel-gpu/hip legs not re-run (S23 rows stand; nothing changed on that side).

Readings:

1. **The S23 headline gap is closed.** S23 recorded chapel-48-core 60× ahead of single-thread flow at N=512; today at N=1024 f32 the same chapel `forall` and flow's orchestrator are at **parity, flow ahead** (184.0 vs 192.7), and flow is 18× past single-thread C++. The parallel-first idea is now a measured fact on CPU: same `.flow` source, execution-graph paths + sliced bulk sites, output byte-equal to the oracle.
2. **Self-speedup 19.1×** (f32@1024) against the same binary at `FLOW_PAR=1` — on a ≈48-core quota with a 384-thread pool; the scheduler holds its own under 8× thread oversubscription.
3. **f64@1024 sits 1.44× behind chapel** — but chapel's own f64 beat its f32 by 1.39× on this run (138 vs 193), a width inversion that reads as qthreads/box variance; re-measure before treating as signal.
4. **The ≤512 distance is the startup floor, not compute:** flow wall carries ≈11 ms of process+pool spawn (the N=16 row) that per-iteration baselines exclude by construction. Floor-adjusted, 512 f32 is ≈3× behind chapel's compute number. Knobs recorded, not built: spawn the pool at quota width (cgroup-aware count or `FLOW_PAR=48`) instead of host-visible 384; a `FLOW_PERF`-analog compute timer for the llvm leg would end the wall-vs-compute estimate game (S19 item #19's CPU twin).
5. **Why numpy is 130× ahead of everyone naive (not just flow):** numpy calls BLAS (OpenBLAS here) — loop tiling to cache, packed panels, AVX FMA microkernels, threads. That is a different *algorithm class*: the same 2N³ FLOPs at ~50–100× better constants. The honest peers agree: single-thread cpp (3,334 ms) and rust (3,247 ms) are equally ~2,300× behind numpy at 1024. Same story as cuBLAS vs every naive GPU kernel (24× at 4096). Closing THAT gap means tiling/blocking in the emitter or a BLAS-class library seam — an algorithm decision for Sapir, not codegen tuning.
6. **Why chapel still wins ≤512 (and not at 1024):** both run the same naive per-cell algorithm multicore, so the ≤512 gap is not algorithm. Decomposition at 512 f32 (flow 26.9 wall vs chapel 5.27 compute): (a) ≈11 ms pool-spawn floor — measurement kind + the 384-thread spawn, item 1's knob; (b) the remaining ≈3× compute gap is mostly **per-element bounds guards in the fold body** — the captured-array indices (`a[i*512+k]`, `b[k*512+j]`) are unproven through the by-ref capture Proj (`bounds_proof` limitation, recorded as backend-llvm suggestion #9), so every inner-loop iteration pays two guarded index checks; chapel `--fast` compiles all checks OFF. Plus residual alloca/store-load emitter traffic clang's sroa doesn't fully fold. At 1024 the working set (12 MB) leaves cache, DRAM bandwidth dominates, the guard/residue cost hides behind memory stalls — and flow lands at parity/ahead. So: the compute-bound small-N gap has a named owner (#9 proofs → guards drop, emitter unchanged — the consumer is already plan-driven), and the memory-bound regime is already won.

## The fmad measure (where it lives, and what this box adds)

The `-fmad=false` price was **measured in S23** (`matmul/s23.md`, GPU tables): flow pins FMA off for oracle bit-parity (DESIGN §4); chapel-gpu/nvcc default it on. The S23 cells: **f64@4096 flow 232.4 ms vs chapel-gpu 114.2 = 2.0×** — while f32 sits at parity with both naive-CUDA and chapel-gpu (memory-bound, FMA-indifferent). This box confirms the shape from the f64÷f32 column above: the ratio grows from 1.0× (launch floor) to **4.2–4.3× at saturation** — f64 pays both the double-width memory cost (~2×) *and* the halved non-FMA issue rate; the FMA half is the recoverable part. The **decision** (a labeled `-fmad=true` non-oracle perf row) is standing for Sapir — S25 item 2; the naive-cuda-f64 column will make it a three-way like-for-like when the next box runs.
